# 门限签名协议（三）：门限 EdDSA 与 Ed25519 输出兼容性

“支持门限 Ed25519”可能指几件不同的事：输出能被 Ed25519 验证器接受，沿用某种 Ed25519 密钥表示，或者复现单机算法的全部签名过程。这些目标并不等价。

门限协议通常希望保持外部签名格式与验证关系，同时改变内部密钥生成和 nonce 生成方式。FROST 的 Ed25519 密码套件提供了一个清晰实例：其签名兼容相应验证规则，但签名生成不是单机 Ed25519 的确定性流程。

## 一、先分清 seed、秘密标量与份额

RFC 8032 的单机 Ed25519 从 32 字节随机 seed 开始。seed 经过 SHA-512 展开，前半部分按规则清位和置位后形成秘密标量，后半部分作为秘密 prefix 参与 nonce 派生。

设基点为 B、其素数阶为 L，秘密标量为 a，公钥为 A：

$$
A=aB.
$$

门限系统可以直接通过 DKG 产生分布式秘密标量及公钥，并不一定存在一份单机 seed。各方持有的是标量域中的份额，而不是能够分别调用普通 Ed25519 API 的“小 seed”。

因此，不应把份额各自执行 clamping，再相加，期待得到正确的门限密钥。clamping 是特定 seed 展开流程中的位处理规则，不是对任意 Shamir 份额的通用操作。

## 二、输出兼容的核心是消息、挑战与编码一致

以纯 Ed25519 为例，其基本结构可以写为：

$$
\begin{aligned}
R&=rB,\\
h&=\operatorname{LEInt}
\bigl(\operatorname{SHA512}(\operatorname{enc}(R)
\parallel\operatorname{enc}(A)\parallel M)\bigr)\bmod L,\\
S&=r+ha\pmod L.
\end{aligned}
$$

外部签名是 R 的 32 字节的点编码和 S 的 32 字节小端编码拼接。公钥也是 32 字节的点编码。

对于诚实生成的素数阶子群元素，签名满足普通线性关系：

$$
SB=R+hA.
$$

RFC 8032 的完整验签还涉及输入解码、S 的范围，以及带余因子的群等式。FROST Ed25519 套件对协议内元素还规定非单位元和素数阶子群检查。因此，接口不能只保留一个“验签成功”布尔值而省略规范要求。

Ed25519ctx 和 Ed25519ph 具有不同的域分离及消息处理方式，不能把纯 Ed25519 输出兼容性直接推广到这些变体。

## 三、为什么不能直接复制确定性 nonce

单机 Ed25519 使用秘密 prefix 和消息派生 nonce。一个进程同时掌握这些秘密，并按单机算法的一致流程执行。

多方环境中，参与方会看到其他人的承诺，并可能控制消息包、调度和并发会话。直接让每方用“份额加消息”确定性派生 nonce，不等于复制了单机安全证明。

如果同一秘密 nonce 在两份不同挑战响应中重复出现，就可能通过相减消去 nonce，并恢复长期秘密或其份额。避免最终签名重复，并不足以避免某个参与方的局部 nonce 重复。

FROST Ed25519 采用其门限协议规定的随机化 nonce 和绑定因子，最后产生能够由相应 Ed25519 验证器检查的签名。**相同公钥、消息与验证格式，不要求每次生成完全相同的签名字节。**

## 四、一次门限 Ed25519 签名的数据流

建钥后，各方认可同一个公钥、密码套件、标识和份额验证公钥。本次签名的主要步骤如下：

1. 参与者生成本协议的一次性秘密 nonce，并发送公开承诺。
2. 协调者提供消息及完整承诺列表；参与者核对业务消息和本地状态。
3. 各方按套件计算绑定因子、聚合点、Ed25519 兼容的挑战和本地签名份额。
4. 验证份额，聚合最终标量，再编码为 64 字节签名。
5. 使用目标链或目标系统的实际验证器核对，并确认签署的消息字节没有变化。

其中，最后一步不能用“同一把公钥在另一个工具里能验签”替代。不同实现可能对非规范编码、小阶点或边界输入采用不同接受规则，互操作测试应明确这些差别。

## 五、一个真实兼容性验证例子

RFC 9591 附录 E.1 给出三方、门限为二的 FROST Ed25519 测试向量。本次参与者标识为 1 和 3，消息是四字节 ASCII 文本 test。

以下是该向量的公开数据；十六进制用于表达字节，不是数学公式。

    public_key:
    15d21ccd7ee42959562fc8aa63224c8851fb3ec85a3faf66040d380fb9738673

    message_hex:
    74657374

    signature:
    36282629c383bb820a88b71cae937d41f2f2adfcc3d02e55507e2fb9e2dd3cbe
    bd9d2b0844e49ae0f3fa935161e1419aab7b47d21a37ebeae1f17d4987b3160b

签名的两行应按字节直接拼接，总长度为 64 字节。使用普通 Ed25519 公钥验证接口，可以验证这份门限协议生成的签名。本例已用 Python cryptography 的 Ed25519 验证接口核对通过。

这个实验验证的是最终输出兼容性，不能据此证明份额安全、nonce 状态机或参与方通信已经正确。那些性质需要另外检查门限协议。

## 六、迁移与备份时的表示边界

如果系统从既有单机 seed 迁移，应明确究竟分享什么：seed 本身、展开后的标量，还是协议需要的其他秘密。分享 seed 后再重构调用单机签名，与不重构私钥的门限签名有不同的安全边界。

反过来，DKG 产生的标量份额也未必能够导出为一份传统 seed，因为 SHA-512 展开与位处理不提供这种可逆关系。备份与恢复应针对协议状态设计，不能只规定“导出 32 字节”。

份额刷新、派生与升级还必须保持目标公钥、标量域、消息变体和验证规则的一致。验证方兼容，是设计目标之一；长期秘密怎样分布和使用，是另一组独立问题。
