# 数字签名（五）：Ed25519 的种子、标量与编码规则

Ed25519 的实现错误，常发生在“私钥”这个词掩盖了不同对象时。32 字节种子、修剪后的标量、扩展秘密材料，以及某些接口的 64 字节私钥格式，都可能被统称为私钥。

实现与审查的第一步，是给每个对象明确的名称、长度、字节序和用途，再核对转换流程。

## 一、从种子开始，而不是从任意标量开始

RFC8032 的 Ed25519 建钥输入是 32 字节随机种子。先计算 SHA-512，得到 64 字节扩展材料，前半部分用于形成标量，后半部分用于 nonce 前缀。

这一过程不能倒置。知道标量，并不意味着能够恢复原种子；知道种子则可以重新计算标准流程需要的全部材料。

有些库使用“种子加公钥”组成的 64 字节结构，另一些接口可能接受扩展密钥。长度同为 64 字节不代表布局一致。导入前应核对 API 文档，而不是截取前 32 字节试验。

## 二、比特修剪究竟改了什么

对 SHA-512 结果的前 32 字节，Ed25519 执行规定的修剪：清除第一个字节的最低三位，清除最后一个字节的最高位，并设置其第二高位。

用操作表示为：

~~~text
a_bytes[0]  &= 248
a_bytes[31] &= 63
a_bytes[31] |= 64
~~~

这是字节处理代码，不是对任意数学私钥的通用修复步骤。之后按小端规则把这 32 字节解释为整数 a。

修剪后的整数具有特定比特形状，并且是 8 的倍数。它不要求小于基点素数阶；在标量运算中按子群阶处理，与保存原修剪字节是两项不同操作。

直接对一个已有标量重新修剪，通常会改变公钥。若系统做加法式派生，也不能假设派生标量仍具有标准种子展开产生的比特形状。

## 三、标准测试向量如何帮助定位错误

RFC8032 的空消息向量使用下面的公开教学种子：

~~~text
9d61b19deffd5a60ba844af492ec2cc44449c5697b326919703bac031cae7f60
~~~

按标准流程计算得到公钥：

~~~text
d75a980182b10ab7d54bfed3c964073a0ee172f3daa62325af021a68f707511a
~~~

本篇独立重算后，修剪标量的小端字节为：

~~~text
307c83864f2833cb427a2ef1c00a013cfdff2768d980c0a3a520f006904de94f
~~~

第一个字节为 30，最后一个为 4f，均为十六进制。前者低三位为零，后者最高位为零、第二高位为一，符合修剪规则。

这些向量中的秘密已经公开，只能用于测试。检查时应先对上种子哈希与公钥，再继续签名；否则一个最终验签失败可能同时掩盖多个转换错误。

## 四、公钥存储的主要是纵坐标

Ed25519 公钥是点 A 的 32 字节编码。其主要内容是纵坐标 y 的小端表示，并把横坐标 x 的最低位放入最后一个字节的最高位。

这不是完整横坐标，也不是 SEC 1 的“前缀加横坐标”。恢复点时，需要清除符号位、解析 y，再根据曲线方程求出符合位选择的 x。

RFC8032 的解码还包含范围与恢复失败检查。不能无条件把超范围 y 取模，也不能在平方根不存在时继续计算。特定共识协议若允许不同编码，应明确使用该协议的完整验证语义。

原始公钥字节还可能被输入挑战哈希。解析、重新编码和哈希之间，应保持规范要求的一致性。

## 五、签名的两半具有不同含义

Ed25519 签名共 64 字节：前半部分是点 R 的编码，后半部分是标量 S 的小端编码。两者虽然都是 32 字节，校验规则却不同。

对于前面的空消息向量，签名为：

~~~text
e5564300c360ac729086e2cc806e828a84877f1eb8e5d974d873e06522490155
5fb8821590a33bacc61e39701cf9b46bd25bf5f0595bbe24655141438e7a100b
~~~

两行是为了阅读而换行，实际是连续 64 字节。第一行需要按点编码解析，第二行需要按整数解析并检查小于子群阶。

不能把两半都当成横坐标，也不能把响应标量像秘密标量一样再次修剪。简单检查最高若干位为零，也不足以替代完整的数值范围检查。

## 六、兼容性要覆盖恶意输入

诚实向量只能验证正常路径。实际审查还要包括长度错误、截断、超范围 S、非法点编码，以及不同余因子验证规则下的边界签名。

RFC8032、特定链的共识规则和某个库的“严格验证”选项，不一定具有完全相同的接受集合。ZIP215 明确说明了这类差异为何会影响共识系统。

因此，替换库或启用批量验签时，除了正常签名互通，还应对比无效和边界输入的接受结果。结果一致性本身就是协议兼容性的一部分。

## 七、密钥类型应保留语义

系统中最好区分种子、扩展秘密、标量、公钥和签名字节的类型与序列化标记。备份也应记录算法实例、格式版本和恢复所需材料，避免未来只剩下一段无法确定含义的十六进制。

秘密前缀与标量都需要保护。公开公钥和签名可以用于测试与审计，但日志不应顺手输出扩展材料。调试向量与真实账户数据也应使用明确不同的来源与目录。

当每个字节串都具有可验证的定义时，算法公式才能可靠地连接到接口和密钥生命周期。
