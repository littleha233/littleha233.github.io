传统口令登录要求服务器判断“你提交的秘密是不是那个秘密”。Passkey 则让服务器保存公钥，并验证本次请求是否获得相应私钥的授权。这个变化降低了共享秘密泄漏的影响，但完整协议还必须回答三个问题：这次授权针对哪个网站、是哪一次请求、以及服务器最终把它绑定到了哪个账户？

## 一、先区分凭据、解锁方式和通信协议

Passkey 是面向用户的公钥凭据。一个账户可以登记多个凭据；同一个凭据也可能由提供方安全同步到多台设备。它并不是用户指纹的另一种编码。

| 组件 | 承担的工作 | 不应混淆的边界 |
| --- | --- | --- |
| RP（依赖方） | 网站后端保存账户、公钥及挑战状态 | 不持有用来认证的凭据私钥 |
| 浏览器或平台客户端 | 检查来源，组织 WebAuthn 请求 | 不能替代服务器的结果校验 |
| Authenticator（认证器） | 管理凭据并执行授权操作 | 不一定是独立 USB 硬件 |
| WebAuthn | 应用调用公钥凭据的接口和数据协议 | 不是一个单独的签名算法 |
| CTAP | 客户端与外部认证器交互的协议 | 不要求网页自己操作硬件私钥 |

指纹、面容、设备 PIN 是认证器确认本地用户的方式，服务器通常收到的是验证结果标志，而不是生物特征数据。是否要求用户验证、支持什么认证器、怎样处理跨设备登录，都是系统配置的一部分。不能看到一个 API 调用就推断“每次必然使用指纹”。

这也解释了 FIDO2、WebAuthn 和 Passkey 的关系：前两者描述标准体系与接口，Passkey 描述用户使用的凭据体验。判断安全属性时，应继续看凭据是否可发现、是否允许同步、是否要求用户验证，而不只看产品按钮的名称。

## 二、网站绑定比“用私钥签个随机数”更重要

设站点是 `https://login.example.com`，配置的 RP ID 为 `example.com`。RP ID 不含协议、端口或路径；origin 则标识实际来源，通常包含协议、主机及非默认端口。两者作用不同。

浏览器会检查调用页面与 RP ID 的关系。假冒站点 `https://example-login.test` 不能仅凭展示相同图标，就请求一个属于 `example.com` 的凭据。服务器还需要检查返回的 origin 是否在自己明确允许的范围内。

认证器数据中包含：

$$
\operatorname{rpIdHash}=\operatorname{SHA256}(\operatorname{RP\ ID}).
$$

客户端数据则描述本次操作的类型、challenge、origin 等。服务器将这些信息与先前保存的预期值比较，才知道验签成功的是“本网站的一次有效认证”。

如果服务端只验证某个任意字符串的签名，即使算法正确，也没有实现完整的 WebAuthn 登录。网站绑定依赖浏览器、认证器和 RP 共同执行各自的检查。

## 三、注册是在可信账户会话里增加一种登录能力

注册开始前，后端必须明确用户身份与允许新增凭据的权限。已有账户可用当前受保护会话；新账户则按站点设计完成初始注册。Passkey 并不要求所有注册都先输入传统口令。

服务端产生随机 challenge，保存其用途、账户绑定、有效期及使用状态，然后返回创建选项。浏览器调用 `navigator.credentials.create({ publicKey: options })`。选项中的 challenge、用户 ID 等二进制字段需要按约定编码，不能把 Base64url 文本直接当原始字节。

认证器创建凭据后返回注册材料。RP 根据规范验证操作类型 `webauthn.create`、challenge、origin、RP ID 哈希、用户在场与所需的用户验证等信息，再关联 credential ID、公钥和账户。公钥的算法、编码和参数也必须经过验证。

这里需要修正一个常见简化：注册不是统一的“私钥对 challenge 签名并附上公钥”。注册响应包含 attestation object；具体 attestation 格式决定如何检查证明材料。采用 `none` attestation 时，不能虚构一个不存在的设备证明签名。普通站点可以选择不收集可识别设备的证明信息，企业也可以按明确策略验证认证器来源。

credential ID 是寻找凭据的标识，不应单独当作登录秘密。真正需要防止的是把攻击者的新公钥错误登记到受害者账户；因此新增、删除凭据和恢复流程都需要充分授权与审计。

## 四、登录签名覆盖的是一组精确字节

登录时，后端创建认证 challenge。浏览器请求认证器使用已登记的凭据，并返回 credential ID、authenticator data、client data JSON 和签名等材料。

用 $A$ 表示收到的 authenticator data 原始字节，用 $J$ 表示 client data JSON 原始字节，则验签消息是：

$$
M=A\parallel\operatorname{SHA256}(J).
$$

服务器用该凭据已登记的公钥验证签名。这里的 $J$ 必须是响应中的原始字节：服务器可以解析 JSON 检查字段，但不能重新序列化 JSON 后拿新字节验签。空格、属性顺序等变化都会影响哈希。

下面是一个仅用来理解数据布局的独立例子：

```text
预期 RP ID：example.com
预期 origin：https://login.example.com
预期操作：webauthn.get
预期 challenge：本次服务器生成并保存的随机字节

authenticatorData：RP ID 哈希（32字节）+ flags（1字节）
                   + signCount（4字节）+ 可选扩展数据
签名消息：authenticatorData + SHA256(clientDataJSON)
```

本例不含扩展的认证 assertion 中，authenticator data 是 37 字节，拼接 32 字节客户端数据哈希后，签名消息是 69 字节。这只是该简化情形的长度核对，不是所有响应长度都固定为 69，也不适用于含凭据公钥等附加数据的注册响应。

challenge 自身通常位于 $J$ 中，因此通过 $\operatorname{SHA256}(J)$ 进入签名消息。RP ID 哈希则直接位于 $A$ 中。两者不是可有可无的装饰字段。

## 五、验签成功只是服务端认证检查中的一步

一个清楚的验证顺序是：首先把响应关联到待处理认证请求，找到预期账户或按可发现凭据的规则解析账户；随后检查 credential ID 和用户句柄是否与登记关系一致；检查 client data 的操作类型、challenge 和 origin；检查 authenticator data 的 RP ID 哈希、标志以及相关扩展；最后按登记的算法与公钥验签，并完成挑战状态的原子更新。

challenge 应不可预测、短期有效并且只能成功消费一次。对于并发认证，同一 challenge 的两次提交不能都因为“读取时还没用过”而创建会话。可以使用事务或比较更新，把最终状态转换与签发会话的前置条件关联起来。

UP 表示用户在场，UV 表示完成用户验证。两者不等价。如果业务要求 UV，前端设置 `userVerification: "required"` 还不够，服务端也必须检查对应返回标志。

签名计数器可提供克隆或状态异常的信号，但并非每种认证器都提供严格递增的计数；同步凭据等场景更不能套用“必须每次加一”的简单规则。处理策略应结合认证器能力和风险模型。

验证通过后才建立应用会话。Cookie 的保护、会话期限、CSRF 防护和敏感操作再认证仍属于应用负责的工作。Passkey 认证成功并不自动授权转账或修改恢复邮箱。

## 六、用三个反例检查协议是否真的绑定了上下文

第一种情况：攻击者重放昨天的完整响应。其签名在数学上仍可能正确，但 challenge 已过期或已经消费，后端应拒绝。这说明防重放依靠状态和挑战验证，不能单靠验签。

第二种情况：请求来自 `https://example-login.test`。即使页面文字一模一样，浏览器不能把它视为 `example.com` 的合法来源；后端的 origin 检查也不应放行。配置过宽的允许来源，会削弱这道边界。

第三种情况：某个真实站点的前端被注入脚本，或者登录后的会话被窃取。Passkey 并不让整个应用免于攻击。攻击者可能在合法来源内诱导操作，也可能绕开认证流程滥用已有会话。因此“抗凭据钓鱼”不能扩写成“社会工程、XSS 和账户盗用都不存在”。

这三个反例分别对应时间、来源和应用权限。审查一套登录系统时，逐个构造反例，比只观察一次正常登录更容易发现漏项。

## 七、同步与恢复改变的是信任范围

设备绑定凭据强调私钥不能离开特定认证器。同步凭据则把加密同步、提供方账户保护、新设备加入和恢复机制纳入信任范围。同步提高可用性，但它的安全性必须连同整个凭据提供方系统评估，不能一概描述为“明文上传私钥”。

还要区分同步和跨设备认证：手机可以帮助另一台电脑完成登录，并不意味着手机上的私钥已经复制到那台电脑。具体产品支持情况会变化，部署时应实测目标平台，避免照搬某个年份的兼容性结论。

对高价值账户，可以登记多枚独立凭据，明确新增凭据、撤销凭据和恢复流程。恢复邮箱或人工客服如果能够绕过强认证直接接管账户，就可能成为整体最弱的一环。钱包系统还需区分“登录管理后台”与“授予链上签名能力”：前者的公钥凭据不能未经策略绑定就代替后者的交易授权。

## 八、温习与进一步阅读

可以用四个问题检验理解：为什么不能把重新序列化的客户端 JSON 拿去验签？为何合法签名仍会因为 challenge 过期而被拒绝？UP 和 UV 的区别是什么？登记新凭据为什么属于敏感账户操作？

回答这些问题需要同时理解密码学消息和服务器状态，而不只是记住 `create`、`get` 两个 API 名字。
